## 1. 설계 목표와 제약

| 구분 | 내용 |
| :--- | :--- |
| **산출물** | 과실 본체·꼭지·잎·줄기를 분할하는 12클래스 세그멘테이션 모델 |
| **정확도 목표** | 숙성도 판별 90%, 파지·절단 포즈 성공률 85%, 1회 순회 미탐지율 15% 이하 |

## 2. 참조 시나리오 캘리브레이션 — 우리는 어디에 있는가

교재 종합 콘솔은 네 가지 시나리오의 권장 설정을 제시한다. 우리 조건을 이 좌표계에 놓으면 설계값의 출발점이 나온다.

| 시나리오 | 조건 | 권장 설정 |
| :--- | :--- | :--- |
| 야생동물 4종 | 1,500장 · 유사 도메인 | `n` / `freeze=10` / batch 32 / imgsz 640 / mosaic 0.5 / cache RAM / amp on / epochs 150 |
| 제품 불량 검출 | 400장 · 유사 · **객체 작음** | `n` / `freeze=23` / batch 16 / **imgsz 1280** / **mosaic off** / cache RAM / amp on / epochs 120 |
| 뇌 MRI 종양 | 1,000장 · **완전 다른 도메인** | `n` / `freeze=None` / batch 16 / imgsz 640 / mosaic 0.5 / epochs 200 |
| 물류 창고 화물 | 50,000장 · 유사 | `s` / `freeze=None` / batch 64 / imgsz 640 / mosaic full / epochs 300 |

**우리 부트스트랩 단계의 위치**: 데이터 규모는 "야생동물"(1,500장·유사)과 같고, **객체 크기는 "제품 불량"**(작음)과 같다. 두 시나리오의 처방을 합성해야 한다.

| 축 | 참조 | 우리 값 |
| :--- | :--- | :--- |
| 모델 크기 | 두 시나리오 모두 `n` | **`n`** — Edge 예산까지 겹쳐 이견 없음 |
| 프리징 | 야생동물 `10` / 불량 `23` | **`10`** — 1,500장은 400장보다 여유가 있다 |
| 증강(mosaic) | 야생동물 0.5 / 불량 off | **0.5에서 시작, 0.0까지 낮춰 비교** |
| 해상도 | 야생동물 640 / 불량 1280 | **충돌 — 3.4절에서 별도 판단** |
| epochs | 150 / 120 | **150** (기존 계획의 300에서 하향, 3.2절) |

교재가 "일부러 엉망인 설정"으로 제시하는 조합(`m` 모델 / `freeze=none` / batch 8 / imgsz 1280 / mosaic full / cache off / amp off / epochs 600)과 대조하면, 우리 설계가 피해야 할 방향이 명확해진다 — **큰 모델 + 프리징 없음 + 작은 배치 + 과도한 증강 + 캐시·AMP 미사용 + 과도한 에폭**.

## 3. 하이퍼파라미터 설계

### 3.1 전이 설계 — 무엇이 넘어오고 무엇이 새로 학습되는가

클래스 수가 6에서 12로 바뀌어도 **재초기화되는 것은 마지막 분류 컨볼루션뿐**이고 백본·넥·공유 헤드는 전부 전이된다. 즉 클래스 재설계가 "처음부터 다시"를 뜻하지 않는다.

**출발 가중치**: `exp-2.pt`(Laboro Tomato 학습본)를 주 후보로, `yolo26n-seg.pt`(COCO)를 대조군으로 A/B 비교한다. 같은 작물의 형상·질감·배경에 이미 적응된 쪽이 도메인상 유리하다.

**스크래치 학습은 후보에 두지 않는다.** 교재는 SAR 위성영상·초음파·열화상처럼 **픽셀 통계 자체가 자연 이미지와 다른** 경우에만 스크래치를 검토할 수 있다고 한정한다. 온실 RGB는 전형적인 자연 이미지이므로 이 예외에 해당하지 않으며, 순서는 항상 파인튜닝이 먼저다.

**클래스 매핑** — 3단계에서 6단계로 가는 것은 세분화이므로 일부는 개념이 대응된다. 대응 인덱스를 맞추면 그 분류 가중치를 물려받을 수 있으나 **자동이 아니라 직접 해야 한다.**

| 베이스라인 | 신규 | 처리 |
| :--- | :--- | :--- |
| `l_green` | `green` | 승계 |
| `l_fully_ripened` | `red` | 승계(근사) |
| `l_half_ripened` | `breaker`/`turning`/`pink` | **1:3 분화 — 승계 불가, 재초기화** |
| `b_*` (대과) | 없음 | 폐기 |

> 이름·인덱스 조정은 로드 후 **메모리 상에서만** 수행한다(`model.names[idx] = ...`). `.pt`를 덮어쓰면 원본 가중치를 되돌릴 수 없다.

### 3.2 epochs와 patience — 상한과 실제 종료를 분리한다

`patience` 기본값 100은 파인튜닝에 과도하다. 사전학습 모델은 빨리 수렴해 30에폭 부근에서 최고점을 찍고 남은 에폭을 태운다. **`patience=10~20`으로 낮춘다.**

**`epochs`를 150으로 정하는 데는 조기 종료와 별개의 이유가 있다.** `epochs`는 종료 시점만 정하는 값이 아니라 **학습률 스케줄의 전체 길이**를 정한다. `lrf`는 "마지막 에폭에서의 학습률 비율"이므로, `epochs=300`으로 두고 50에폭에 조기 종료하면 학습률이 계획된 감쇠 곡선의 앞부분만 밟고 끝난다 — 즉 조기 종료가 되더라도 상한을 잘못 잡으면 학습률 궤적 자체가 달라진다. 따라서 상한은 실제 수렴 지점에 맞춰 정한다.

| 항목 | 값 | 근거 |
| :--- | :--- | :--- |
| `epochs` | 150 (부트스트랩) / 200~300 (본 학습) | 데이터 증가에 맞춰 상향 |
| `patience` | 15 | 파인튜닝 수렴 속도 |
| `warmup_epochs` | **기본 3 유지** | 잘 학습된 가중치로 시작하므로 첫 배치의 큰 학습률이 그 가중치를 흐트러뜨린다. 파인튜닝이라고 0으로 줄이지 않는다 |
| `lrf` | 기본값 | 종료 구간 감쇠 |

### 3.3 옵티마이저 — `auto`가 학습률을 덮어쓴다

가장 많이 걸리는 함정이다. `optimizer=auto`는 총 반복 횟수(`epochs × 이미지수 / batch`)를 계산해 옵티마이저를 고르고 **학습률까지 스스로 정한다.** 사용자가 준 `lr0`는 조용히 무시된다.

| 상황 | 설정 |
| :--- | :--- |
| 기본 학습 (학습률 미개입) | `optimizer` 생략 — YOLO26은 MuSGD 계열이 선택된다 |
| **`lr0`를 직접 제어** (2단계 파인튜닝 Stage 2 등) | **`optimizer`를 반드시 명시** |

MuSGD는 SGD에 Muon을 섞은 하이브리드로, 대형 언어 모델 학습에서 비전으로 넘어온 방식이며 큰 스케일에서 수렴이 안정적이다.

### 3.4 해상도 설계 — 소형 객체와 지연 예산의 충돌

교재의 소형 객체 처방은 `imgsz=1280`이다. 그런데 우리는 배포 입력이 640×640 stretch로 고정되어 있다(`inference_config.json`). **학습과 추론의 `imgsz`는 일치해야 하므로, 해상도 상향은 배포 규격 변경과 Edge 추론 시간 증가를 동반한다.**

이것은 하이퍼파라미터 조정이 아니라 **예산 배분 결정**이다. 따라서 실험으로 판단한다.

| 후보 | 기대 | 비용 |
| :--- | :--- | :--- |
| 640 (현행) | 배포 규격 그대로, 지연 여유 | 14~30px 객체에 불리 |
| 960 | 소형 객체 정확도 개선 | 추론 시간 증가 — 5초 예산 재확인 필수 |
| 1280 | 교재의 소형 객체 처방 | 증가폭이 커 Edge에서 예산 초과 위험 |
| 640 + 타일링 추론 | 실질 해상도 상향 | 타일당 추론이라 호출 횟수 증가 |

**판단 기준**: 정확도 향상분(숙성 혼동행렬·과실 recall)과 Jetson 실측 추론 시간을 함께 기록해, **5초 예산 안에서** 최선을 고른다. 데스크톱 GPU 수치로 결정하지 않는다.

### 3.5 증강 설계 — 과도한 증강이 정체의 원인이 된다

교재는 소형 데이터셋에서 **증강 과도**를 mAP 정체의 독립적 원인으로 지목하고 `mosaic=0.5` 또는 `0.0`을 처방한다. 우리 부트스트랩(1,500장)이 정확히 그 구간이다.

| 인자 | 설계값 | 근거 |
| :--- | :--- | :--- |
| `hsv_h` | **0.0 (금지)** | 숙성 단계 라벨의 근거가 색이다. 색을 흔들면 정답이 틀린 데이터가 된다 |
| `hsv_s` | 0.2 (약하게) | 발색 정도가 판정 근거 |
| `hsv_v` | 0.5 (적극) | 시간대·그림자 변동은 실제로 일어나고 색은 보존된다 |
| `mosaic` | **0.5** → 0.0 비교 | 소형 데이터셋 과증강 회피 |
| `close_mosaic` | 사용 | 학습 후반 모자이크 종료 |
| `copy_paste` | **0.4** (`mode="flip"`) | 세그멘테이션 전용 증강. 잎·과실 인스턴스를 합성해 **가림·밀집을 인위적으로 늘린다** — 최상위 리스크에 직접 대응 |
| `scale` | 사용 | 내용 배율 변화(입력은 640 고정), 비용 거의 없음 |
| `multi_scale` | **False** | 입력 텐서 크기를 480~800으로 흔드는 인자. 배포 해상도가 단일이므로 학습만 느려지고 얻는 것이 없다 |

`scale`과 `multi_scale`은 이름이 비슷하나 층위가 다르다 — 전자는 증강(피사체를 앞뒤로 움직임), 후자는 샘플링(카메라 센서 크기를 바꿈)이다.

### 3.6 프리징 설계 — 두 축으로 단계마다 다르게

`freeze=N`은 레이어 0~(N−1)을 얼린다. YOLO26 백본은 0~10이므로 `freeze=10`은 마지막 C2PSA 블록을 학습 상태로 남기고, 완전 동결은 `freeze=11`이다.

**데이터 양**은 "얼마나 학습시켜도 되는가"를, **도메인 유사도**는 "기존 특징이 쓸모 있는가"를 정한다. 두 축은 독립이다.

| 단계 | 데이터 | 도메인 | 설계값 |
| :--- | :--- | :--- | :--- |
| 부트스트랩 | 1,500장 | 유사 | **`freeze=10`** |
| 본 학습 | 5,000장 | 유사 | **`freeze=None`** (10과 비교) |
| 일반화 | 10,000장 | 유사(계절 확장) | **`freeze=None`** |

**2단계 파인튜닝**: 데이터도 적고 도메인도 먼 최악의 경우용 기법이다. 우리 도메인은 COCO와 크게 다르지 않아 필수는 아니나, 클래스가 6→12로 크게 바뀌고 부트스트랩 데이터가 적으므로 부트스트랩에서 단일 단계와 A/B 비교할 가치는 있다.

```
Stage 1  freeze=11              → 헤드를 진정시킨다. 높은 성능을 기대하지 않는다
Stage 2  freeze=None, lr0≤0.001 → 백본까지 도메인에 맞춘다 (optimizer 명시 필수, 3.3절)
```

항상 이기는 기법이 아니라 학습 불안정을 줄이는 선택지이며, 조건에 따라 단일 단계가 이길 수도 있다.

### 3.7 클래스 불균형 설계

예외 클래스(`over_ripe`·`cracked`·`malformed`)는 자연 발생률이 낮은 롱테일이다. mAP는 클래스별 평균이므로 희귀 클래스 하나가 전체를 크게 깎는다.

교재 설명에 따르면 클래스 가중치는 **빈도의 역수에 지수 `cls_pw`를 적용**하고(`(1/클래스별 개수)^cls_pw`) 평균이 1이 되도록 정규화된다. 즉 `cls_pw=0`이면 전 클래스 동일 가중, 값이 커질수록 희귀 클래스에 더 큰 가중이 걸린다. **`0.25`에서 시작**하고, 그래도 희귀 클래스가 잡히지 않으면 `1.0`까지 올린다.

## 4. 처리량 설계 — 실험 횟수가 곧 최종 성능

학습이 3시간이면 하루 3번, 40분이면 12번 실험한다. 속도 최적화는 편의가 아니라 **성능을 사는 일**이다.

| 인자 | 설계값 | 주의 |
| :--- | :--- | :--- |
| `batch` | **`-1`** (VRAM 자동 산정) | 수동으로 찾을 때는 OOM까지 올린 뒤 한 단계 내린다. GPU는 병렬 장치이므로 배치가 작으면 코어 대부분이 놀고 있다 |
| `cache` | RAM 여유 시 `True` | **첫 에폭에는 효과가 없고 오히려 느리다**(캐시 생성 비용). 2에폭째부터 빨라지므로 짧은 벤치마크로 판단하면 효과를 못 본다. RGB+Depth라 용량이 크므로 RAM 확인 필수 |
| `amp` | **`True` 유지** | 대부분 16비트로 계산하고 가중치 갱신 순간만 32비트로 되돌린다. 끄면 느려지고 VRAM도 더 쓰는데 정확도 이득이 없다 |
| `fraction` | 파일럿에만 `0.1` | **절대 성능 판단용이 아니다.** 후보 A/B의 순위를 보는 정도로만 쓴다 |
| `device` | 단일 GPU | 데이터 규모가 분산 학습을 요구하는 수준이 아니다 |

`fraction`의 실질 가치는 사고 예방이다 — `data.yaml` 경로 오타로 val이 빈 상태로 몇 시간을 태우는 일이 흔하다. 우리는 NDJSON→YOLO 변환 단계가 끼어 있어 이 위험이 더 크다.

## 5. 학습 설정 (부트스트랩 기준)

```python
from ultralytics import YOLO

# 도메인이 더 가까운 베이스라인에서 출발 (3.1절). COCO 사전학습과 A/B 비교한다.
model = YOLO("exp-2.pt")

model.train(
    data="cherry_tomato.yaml",   # 12클래스
    epochs=150,                  # LR 스케줄 길이까지 정하는 값 (3.2절)
    patience=15,                 # 기본 100은 파인튜닝에 과도
    imgsz=640,                   # 배포 규격과 일치. 상향은 별도 실험 (3.4절)
    batch=-1,                    # VRAM 자동 산정 (4절)
    cache=True,                  # RAM 여유 확인 후
    amp=True,                    # 기본값 유지
    device=0,
    freeze=10,                   # 소규모 + 유사 도메인 (3.6절)
    cls_pw=0.25,                 # 예외 클래스 롱테일 (3.7절)

    # 증강 (3.5절)
    hsv_h=0.0,                   # 색상 지터 금지 — 숙성 라벨의 근거를 파괴한다
    hsv_s=0.2,
    hsv_v=0.5,
    mosaic=0.5,                  # 소형 데이터셋 과증강 회피
    copy_paste=0.4,              # 가림·밀집 합성
    multi_scale=False,           # 배포 해상도 단일

    # optimizer 미지정(auto). lr0를 주려면 반드시 명시 (3.3절)
)
```

## 6. 실험 설계 — 무엇을 어떤 순서로 비교하는가

**한 번에 하나씩만 바꾼다.** 두 개를 동시에 바꾸면 어느 것이 효과였는지 알 수 없다.

| 순서 | 실험 | 비교 | 판단 지표 |
| :--- | :--- | :--- | :--- |
| E0 | 파일럿 | `fraction=0.1` 1회 | 설정이 돌아가는가(성능 판단 아님) |
| E1 | 출발 가중치 | `exp-2.pt` vs `yolo26n-seg.pt` | 수렴 속도 + 최종 val |
| E2 | 프리징 | `10` vs `None` vs `23` | val mAP + 과적합 격차(train-val) |
| E3 | 증강 강도 | `mosaic` 0.5 vs 0.0 | val mAP |
| E4 | 해상도 | 640 vs 960 vs 1280 | 과실 recall + **Jetson 실측 추론 시간** |
| E5 | 불균형 보정 | `cls_pw` 0.25 vs 1.0 | 예외 클래스별 AP |
| E6 | 2단계 파인튜닝 | 단일 vs 2단계 | 학습 안정성 + 최종 val |
| E7 | 세대 비교 | YOLO26n-seg vs YOLO11-seg | 소형 객체 이득 실측 |

E1~E3은 부트스트랩 단계에서, E4~E7은 본 학습 단계에서 수행한다. 모든 실험은 MLflow에 설정·지표·데이터셋 스냅샷(DVC)을 함께 기록한다.

## 7. 데이터 다양성 설계 — "양"이 아니라 "상황의 가짓수"

교재가 mAP 정체의 **가장 흔한 원인**으로 지목하는 것은 모델이 아니라 데이터 다양성 부족이다.

> 같은 장소, 같은 조명에서 찍은 1,000장은 서로 다른 조건 200장보다 못하다.

이 원칙이 수집 계획의 조건 매트릭스와 정확히 맞물린다. 따라서 데이터 관리 지표를 **장수**가 아니라 **조건 조합의 충족률**로 둔다.

| 축 | 수준 | 관리 |
| :--- | :--- | :--- |
| 시간대 | 오전 / 정오 / 오후 | 각 수준 최소 비율 확보 |
| 전정 수준 | 적극 / 표준 / 최소 | 가림 정도의 분포 |
| 트러스 높이 | 낮음 / 중간 / 높음 | 촬영 각도 다양성 |
| 생육 단계 | 초기 / 성기 / 후기 | 과실 크기·색상 변동 |
| 밀집도 | 낮음 / 중간 / 높음 | 인접 과실 경계 난이도 |

부족한 조합이 남아 있는 상태에서 장수만 늘리면 정체가 풀리지 않는다.

## 8. 평가 설계

`mAP`는 모든 오분류를 동등하게 취급하지만, 본 과제에서 비용은 **비대칭**이다.

| 오분류 | 결과 | 비용 |
| :--- | :--- | :--- |
| 미숙 → 완숙 판정 | 익지 않은 과실 수확 | **높음** — 되돌릴 수 없다 |
| 완숙 → 미숙 판정 | 수확 건너뜀 | 중간 — 차기 순회에서 회수 |
| 인접 단계 혼동 | 등급 편차 | 낮음 |
| 꼭지 미검출 | Stage B 전량 스킵 | **높음** — 수확 0건 |

| 모델 지표 | 대응 KPI |
| :--- | :--- |
| 6×6 숙성 혼동행렬(인접/비인접 분리) | 숙성도 판별 정확도 90% |
| 과실 recall(가림 비율 구간별 분해) | 1회 순회 미탐지율 15% 이하 |
| `pedicel` recall + 축 각도 오차(deg) | 파지·절단 포즈 성공률 85% |
| 예외 클래스 precision | 손상률 5% 이하 |
| **Jetson 실측 추론 시간** | 비전 추론 5초 |

**최종 검증은 모델 단독 지표가 아니라 파이프라인 결합 산출이다.** 학습 모델을 `harvest_pipeline`에 주입해 수확 대상 산출 수를 규칙 기반 베이스라인과 같은 프레임에서 비교한다.

## 9. 진단 프로토콜 — 확인이 빠른 것부터

### 9.1 아무것도 예측하지 못할 때

| 순서 | 확인 | 소요 | 방법 |
| :--- | :--- | :--- | :--- |
| 1 | 신뢰도 임계값이 높은 것뿐인가 | 30초 | `conf=0.1`로 낮춰 본다. 뭐라도 나오면 모델은 살아 있고 성능 문제다 |
| 2 | `data.yaml` 경로가 어긋나 라벨을 0개로 읽는가 | 30초 | `yolo detect val`을 돌려 로그의 `Scanning ... images, ... labels` 확인 |
| 3 | `nc`와 라벨 클래스 번호 범위가 맞는가 | 1분 | `data.yaml`의 `nc` vs `labels/*.txt` 첫 열의 최댓값 |
| 4 | 데이터가 그냥 너무 적은가 | — | 수집 단계로 되돌아간다 |

2번이 가장 악질인 이유는 **에러가 나지 않는다**는 점이다. 라벨을 0개 찾고 그대로 조용히 학습이 끝난다. 그래서 **학습 전 `val` 1회 실행을 게이트로 고정**한다.

### 9.2 mAP가 일찍 정체될 때

에폭을 늘리는 것은 거의 답이 아니다. 이미 평평해진 곡선은 더 돌려도 평평하다.

| 순위 | 원인 | 처방 |
| :--- | :--- | :--- |
| 1 (가장 흔함) | 조명·각도·배경 다양성 부족 | 조건 매트릭스의 빈 칸을 채운다 (7절) |
| 2 | 클래스 비율 붕괴 | `cls_pw` (3.7절) |
| 3 (소형 데이터셋) | 증강이 과도함 | `mosaic` 0.5 → 0.0 |
| 4 | 객체가 너무 작음 | `imgsz` 상향 — 단 Edge 예산 확인 (3.4절) |

라벨 품질 한계도 후보다. 라벨러 간 일치도가 목표 정확도보다 낮으면 모델 문제가 아니다.

### 9.3 새 클래스는 잡는데 기존 클래스를 잊을 때

치명적 망각(Catastrophic Forgetting)이다. 새 데이터에 없는 클래스는 "이제 필요 없다"로 학습된다 — 모델이 배신한 것이 아니라 그렇게 가르친 것이다.

**우리 경우 대부분 의도된 동작이다.** 베이스라인의 `b_*`(대과)를 버리는 것은 방울토마토 한정 시스템이므로 정상이다. 다만 향후 대과 품종까지 지원하려면 주의해야 한다 — **완벽한 회피는 이전 클래스와 새 클래스를 병합한 종합 데이터셋으로 학습하는 것 하나뿐**이고, 나머지는 모두 망각을 늦추는 완화책이다.

## 10. 체크리스트

### 10.1 학습 전
- [ ] 데이터셋 경로·`nc`·클래스 불균형 진단 실행
- [ ] `yolo detect val`로 **라벨 개수를 눈으로 확인**
- [ ] `fraction=0.1` 파일럿 1회 완주
- [ ] 트러스 ID 기준 그룹 분할 확인(무작위 분할 금지)
- [ ] 컬러차트 동시 촬영 여부 확인

### 10.2 설정
- [ ] 모델은 `n`부터
- [ ] `batch=-1` 또는 VRAM 최대치
- [ ] `cache=True` (RAM 여유 시)
- [ ] `amp=True` 유지
- [ ] `patience=10~20`
- [ ] 수동 `lr0`를 쓴다면 `optimizer` 명시
- [ ] `hsv_h=0.0` 확인 (숙성 라벨 보호)

### 10.3 데이터가 적을 때
- [ ] `freeze=10` 또는 `23`
- [ ] `mosaic=0.5` 또는 `0.0`
- [ ] **모델 크기를 올리지 말 것**

### 10.4 결과가 안 나올 때
- [ ] `conf=0.1`로 먼저 확인
- [ ] 데이터 **다양성** 점검(장수 아님)
- [ ] 불균형이면 `cls_pw`
- [ ] 객체가 작으면 `imgsz` 상향(Edge 예산 동시 확인)

### 10.5 배포 전
- [ ] Jetson **실기**에서 TensorRT 엔진 빌드
- [ ] FP16 → INT8 양자화 전후 **숙성 혼동행렬 재측정**
- [ ] 추론 시간 실측 (5초 예산)
- [ ] 학습 시 resize 방식과 배포 방식 일치 확인(stretch·1/255·RGB)
- [ ] 파이프라인 결합 평가로 수확 대상 산출 수 확인

## 11. 설계 요약

| 항목 | 설계값 | 결정 근거 |
| :--- | :--- | :--- |
| 모델 | YOLO26n-seg | 소형 객체 개선 + NMS-free + Edge 예산 |
| 크기 | `n` 고정 | 데이터 규모·추론 예산 양쪽 제약 |
| 출발 가중치 | `exp-2.pt` (COCO와 A/B) | 같은 작물 도메인 |
| 프리징 | 10 → None (단계별) | 소규모+유사 → 데이터 증가에 따라 완화 |
| epochs / patience | 150 / 15 | LR 스케줄 길이 + 파인튜닝 수렴 속도 |
| 옵티마이저 | auto (lr0 제어 시 명시) | `auto`가 `lr0`를 덮어쓰는 함정 회피 |
| 해상도 | 640 출발, 상향은 실험 | 소형 객체 이득 vs 5초 예산 |
| 증강 | `hsv_h=0`, `mosaic=0.5`, `copy_paste=0.4`, `multi_scale=False` | 색상 라벨 보호 + 과증강 회피 + 가림 합성 + 단일 배포 해상도 |
| 불균형 | `cls_pw=0.25` | 예외 클래스 롱테일 |
| 처리량 | `batch=-1`, `cache=True`, `amp=True` | 실험 횟수 확보 |
| 데이터 관리 지표 | 장수 → **조건 조합 충족률** | 다양성 부족이 정체의 최대 원인 |

**설계의 핵심 판단 두 가지**
1. **해상도(3.4절)** — 소형 객체 처방(`imgsz` 상향)과 Edge 5초 예산이 정면으로 충돌한다. 하이퍼파라미터가 아니라 예산 배분 문제이므로 Jetson 실측으로만 결정한다.
2. **증강(3.5절)** — 일반적 처방과 반대로 색상 증강을 **끈다**. 숙성도 라벨의 근거가 색이기 때문이며, 이는 전처리 파이프라인에서 CLAHE를 배제한 것과 같은 이유다.
