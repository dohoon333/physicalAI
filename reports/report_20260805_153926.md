## 1. 왜 세그멘테이션 모델이어야 하는가

전처리 파이프라인(v2)은 두 종류의 마스크를 **반드시** 요구한다.

| 요구 마스크 | 사용처 | 없으면 |
| :--- | :--- | :--- |
| 과실 본체 마스크 | Stage A 부위별 색상 샘플링, Stage B 구 피팅 | 숙성도 판정 근거 소실, 과실 중심 추정 불가 |
| 꼭지(Pedicel) 마스크 | Stage B 꼭지 축 키포인트 회귀 | `SKIP_NO_PEDICEL`로 전량 스킵 — 수확 0건 |

Depth 센서는 과실의 카메라 대향면만 관측하므로 과실 본체 포인트에서 꼭지 방향을 유추할 수 없다. 즉 **꼭지 마스크는 선택이 아니라 파이프라인 동작의 전제 조건**이다. 바운딩 박스만 내는 검출 모델(`yolo26n`)로는 이 요구를 만족할 수 없어 `yolo26n-seg`를 채택한다.

## 2. 모델 선정과 적용 지점

### 2.1 왜 최신 세대(YOLO26)인가

Ultralytics YOLO26은 2026년 1월 릴리스된 최신 세대다. "최신이라서"가 아니라, 이 세대의 개선점이 **본 과제의 병목과 정확히 겹치기 때문에** 선택한다.

| YOLO26의 특성 | 본 과제의 조건 | 왜 직접 이득인가 |
| :--- | :--- | :--- |
| **ProgLoss + STAL** — 소형 객체 인식 개선 | 방울토마토는 400mm 거리에서 약 14~30px | 우리 대상이 정확히 소형 객체다. 이 개선이 가장 큰 단일 이득으로 예상되는 항목 |
| **NMS-free end-to-end 설계** | 비전 추론 5초 예산(PRD 5.1-7) | 후처리 단계가 사라져 Edge 지연이 줄어든다 |
| **DFL 제거로 CPU 추론 최대 43% 향상** | Jetson Orin NX | GPU 외 경로 병목이 줄어 예산 여유가 생긴다 |
| **MuSGD 옵티마이저 기본 적용** | 자체 데이터 1,500~10,000장 (소규모) | 수렴이 빠르고 안정적이라 반복 실험 비용이 낮다. 실험 횟수가 성능을 결정하는 조건(8.9절)에서 중요 |
| **표준화된 TensorRT/ONNX export** | Jetson 배포 필수 | 배포 경로가 짧고, 이미 팀이 Ultralytics NDJSON·Platform으로 데이터를 다루고 있어 학습–배포 도구 사슬이 하나로 이어진다 |

### 2.2 대안 검토 — 왜 다른 선택지가 아닌가

| 대안 | 왜 채택하지 않는가 | 처리 |
| :--- | :--- | :--- |
| YOLOv8-seg / YOLO11-seg | 검증된 세대이지만 소형 객체 손실 개선과 NMS-free가 없다. 우리 조건에서 최신 세대의 이득이 직접적이다 | **A/B 대조군으로 유지** — YOLO26의 이득이 실측되는지 확인해야 하므로 |
| SAM / FastSAM | 프롬프트 기반 범용 분할로 **클래스 개념이 없다.** 숙성 6단계·꼭지 같은 도메인 클래스를 직접 낼 수 없다 | **오프라인 라벨링 보조**로 활용(정답 마스크 초안 생성) |
| Mask R-CNN / Detectron2 | 정확도는 경쟁력 있으나 Edge 실시간에 부적합하고 export 생태계가 약하다 | 제외 |
| GraspNet / AnyGrasp | 애초에 분할기가 아니라 파지 포즈 추정기이며, 강체 부품을 전제한다 | 제외(PRD v2에서 이미 벤치마크 비교군으로 내림) |
| 색상 임계값 기반(현 베이스라인) | 조명 변화에 취약하고, **잎과 색이 겹치는 미숙과는 원리적으로 분리 불가**하다 | 초기 개발용 베이스라인으로만 유지 |

### 2.3 왜 nano 크기인가

두 제약이 같은 방향을 가리킨다.
1. **Edge 추론 예산** — Jetson Orin NX에서 비전 추론 5초를 지켜야 한다.
2. **데이터 규모** — 1,500~10,000장은 큰 모델의 용량을 채우지 못한다. 남는 용량은 학습 데이터 암기(과적합)로 간다(8.1.2절).

정확도가 목표에 미달하면 `s`로 상향하되, **추론 시간 재측정을 전제로만** 허용한다.

### 2.4 파이프라인 어디에 적용되는가

이 모델은 전처리 파이프라인의 **Stage 0 말단에서 트러스(프레임)당 한 번** 호출되고, 그 산출물이 세 갈래로 갈라져 이후 전 단계를 먹인다. 과실 수와 무관하게 호출은 1회다.

```
[Stage 0 공통 전처리]
  색상·Depth 보정 → 하이라이트·그림자 제거 → 구조물 마스킹 → Denoising
        ↓
  ★ YOLO26n-seg 인스턴스 세그멘테이션  ← 모델이 들어가는 지점 (5초 타임아웃)
        │
        ├── 과실 본체 마스크 ──┬──→ [Stage A] 부위별 색상 샘플링 → 숙성 6단계 판정
        │                      └──→ [Stage B] 구 피팅 → 과실 중심 3D 좌표
        │
        ├── 꼭지 마스크 ──────────→ [Stage B] 꼭지 축 키포인트 회귀 → 절단점 유도
        │
        └── 잎·줄기 마스크 ───────→ [Stage B] 충돌 회피 접근포즈 필터링
```

| 산출물 | 소비하는 단계 | 없으면 |
| :--- | :--- | :--- |
| 과실 본체 마스크 | Stage A 숙성도, Stage B 구 피팅 | 판정 근거 소실, 중심 추정 불가 |
| 꼭지 마스크 | Stage B 축 추정 | `SKIP_NO_PEDICEL` — 수확 0건 |
| 잎·줄기 마스크 | 접근 경로 충돌 검사 | 경로를 막는 잎을 못 보고 접근 → 충돌 |

**연결되는 KPI**: 숙성도 판별 정확도 90%(Stage A), 파지·절단 포즈 추정 성공률 85%(Stage B), 1회 순회 미탐지율 15% 이하(과실 recall), 비전 추론 5초(Edge 실측).

### 2.5 코드상 교체 지점과 어댑터 요구사항

파이프라인은 세그멘테이션 모델을 `InstanceSegmentationModel` Protocol로만 참조한다(의존성 역전). 따라서 **주입 인자 한 줄만 교체**하면 나머지 코드는 수정이 필요 없다.

```python
HarvestPreprocessingPipeline(
    config=PipelineConfig.from_yaml("configs/default_pipeline.yaml"),
    segmentation_model=Yolo26SegAdapter("runs/best.pt"),  # ← 여기만 교체
    ripeness_classifier=...,
    pedicel_estimator=...,
)
```

다만 **어댑터가 해야 하는 변환 작업이 있다.** 학습된 12클래스 모델은 인스턴스를 평평한 목록으로 내지만, 파이프라인은 `SegmentationInstance`에 다음 구조를 요구한다.

| 필드 | 요구 사항 |
| :--- | :--- |
| `class_label` | `"fruit"` / `"leaf"` / `"stem"` 중 하나. 숙성 6단계·예외 3클래스는 모두 `"fruit"`로 통합한다(숙성 판정은 Stage A가 다시 수행한다) |
| `mask` | **과실 본체만** — 꼭지를 포함하면 구 피팅 반지름이 과대 추정되어 정상 크기 과실이 범위 초과로 걸러진다 |
| `pedicel_mask` | 꼭지를 **분리 보관**. 없으면 `None` |
| `bbox_xyxy` | 본체 기준 |

가장 까다로운 부분은 **꼭지를 부모 과실에 귀속시키는 일**이다. 모델은 `pedicel` 인스턴스를 독립적으로 낼 뿐 "이 꼭지가 어느 과실 것인지"는 알려주지 않는다. 근접성·접촉 기준으로 매칭해야 하며, 밀집 트러스에서 잘못 귀속되면 **엉뚱한 축으로 절단**하게 된다. 따라서 어댑터는 다음을 명시해야 한다.
- 매칭 규칙(예: 과실 마스크 경계와의 최단거리 + 임계값)
- 귀속이 모호한 경우의 처리 — `pedicel_mask=None`으로 두어 `SKIP_NO_PEDICEL`로 안전하게 빠지게 한다. 억지로 매칭하면 모주 손상 위험이 생긴다.

> **통합 시 확인된 사항**: 이 계획을 검토하며 파이프라인 코드에서 `segment()`가 과실 인스턴스만 반환해 **잎·줄기가 충돌 검사에 도달하지 못하는 배선 누락**을 발견해 수정했다. 규칙 기반 베이스라인은 잎·줄기를 생성하지 않아 잠재 결함으로 남아 있었으나, 12클래스 모델을 주입하는 순간 실제 결함이 되는 지점이었다. 회귀 방지 테스트를 추가했다.

## 3. 현재 확보 상태 (Baseline)

이미 1차 베이스라인이 존재한다.

| 항목 | 내용 |
| :--- | :--- |
| 데이터셋 | Laboro Tomato v1i (Ultralytics NDJSON export), 약 800장, task=segment |
| 클래스 | 6개 — `b_green` / `b_half_ripened` / `b_fully_ripened` / `l_green` / `l_half_ripened` / `l_fully_ripened` (`b`=일반 대과, `l`=방울) |
| 학습 결과물 | `exp-2.pt` (YOLO26n-seg) |
| 입력 규격 | 640×640, stretch resize, RGB, scaling 1/255 |
| 응용 | `tomato-app` — NDJSON 다운로드 → 영상 생성 → 배치 탐지 → 웹 UI/통계 |

베이스라인의 가치는 **파이프라인이 끝까지 도는 것을 확인했다는 점**이다. 이 상태는 실증용이 아니라 전이학습의 출발점으로 쓴다.

## 4. PRD 요구사항과의 격차 — 이 계획의 출발점

공개 데이터셋만으로는 PRD를 만족할 수 없다. 격차를 정확히 규정하는 것이 계획의 핵심이다.

| # | 항목 | PRD 요구 | Laboro Tomato | 조치 |
| :--- | :--- | :--- | :--- | :--- |
| G1 | 숙성 단계 | 표준 **6단계**(Green→Breaker→Turning→Pink→Light Red→Red), 수확 대상은 라이트레드~레드 | **3단계**(green / half_ripened / fully_ripened) | 자체 재라벨링 필수. 3단계로는 "라이트레드와 레드 구분"이 원리적으로 불가 |
| G2 | 꼭지(Pedicel) | Stage B 축 추정에 **필수** | 클래스 없음 | 신규 클래스 신설 — 공개 데이터셋에 사실상 존재하지 않음 |
| G3 | 촬영 환경 | 하이와이어 유인재배 온실, 통로 800~1,200mm, 근접 300~600mm | 촬영 조건 상이 | 도메인 갭. 자체 온실 촬영으로 대체 |
| G4 | 대상 작물 | 방울토마토 **한정** | 일반 대과 + 방울 혼재 | `l_*` 중심 재구성, `b_*`는 보조 학습 데이터로만 활용 |
| G5 | 예외 클래스 | 열과·기형과·과숙 필터링(체크리스트 A-7/A-8) | 해당 클래스 없음 | 신규 클래스 + 의도적 수집 |
| G6 | 규모 | 판별 정확도 90% 목표 | 약 800장 | 증량 필요(6절) |

**G1과 G2가 치명적이다.** G1을 해결하지 않으면 숙성도 판별 정확도 90% KPI 자체를 측정할 수 없고, G2를 해결하지 않으면 파이프라인 Stage B가 모든 과실을 스킵한다.

## 5. 클래스 설계 (신규)

계층을 나눠 설계한다. 한 모델이 과실·꼭지·잎·줄기를 함께 분할해야 Stage 0의 단일 세그멘테이션 호출로 두 트랙이 마스크를 공유할 수 있다.

### 5.1 과실 숙성 6단계 (수확 판정 대상)
`green` · `breaker` · `turning` · `pink` · `light_red` · `red`

### 5.2 예외 클래스 (수확 제외 판정)
`over_ripe`(과숙) · `cracked`(열과) · `malformed`(기형과)

### 5.3 구조 클래스 (Stage B 및 충돌 회피)
`pedicel`(개별 과실 자루) · `leaf`(잎) · `stem`(줄기·화방 주축)

> **주의**: `pedicel`과 `peduncle`(화방 주축)은 다른 부위다. 로봇이 절단하는 대상은 `pedicel`이며, 라벨링 지침에 이 구분을 명시해 라벨러 혼동을 막아야 한다. 실제로 PRD v1에서 이 용어가 혼용되어 있었다.

총 12클래스. 잎·줄기는 접근 경로 충돌 검사에 쓰이므로(전처리 문서 3장) 정확한 경계보다 **존재 영역의 포괄성**이 중요하다.

## 6. 데이터셋 수집 계획

### 6.1 촬영 프로토콜

**RGB만 모으면 안 된다.** 전처리 파이프라인은 RGB-D를 요구하고, Stage B의 구 피팅·축 추정은 Depth 없이는 학습 정답을 만들 수 없다. 따라서 촬영 시 다음을 **동시에** 저장한다.

| 저장 항목 | 형식 | 이유 |
| :--- | :--- | :--- |
| RGB | PNG (무손실) | JPEG 압축 아티팩트가 색상 기반 숙성 판정에 노이즈로 작용 |
| Depth | 16bit PNG(mm) 또는 `.npy` | 3D 역투영·구 피팅 정답 생성 |
| 카메라 내부 파라미터 | JSON (fx, fy, cx, cy) | 역투영 없이는 Depth가 무의미 |
| 화이트 레퍼런스 | ColorChecker 동시 촬영 | 선형 화이트밸런스의 기준. 없으면 채널별 보정을 건너뛰어야 함 |
| 메타데이터 | 트러스ID·구역ID·촬영일시·조도(lux)·전정 수준 | **분할 누출 방지와 조건별 성능 분석의 필수 조건**(6.3절) |

### 6.2 수집 조건 매트릭스

체크리스트(A~H)의 변동 요인을 학습 데이터가 실제로 덮어야 한다. 아래 조합을 균형 있게 채운다.

| 축 | 수준 |
| :--- | :--- |
| 시간대 | 오전 / 정오 / 오후 (조도·색온도 변동, C-3) |
| 전정 수준 | 적극 / 표준 / 최소 (가림 정도, B-4) |
| 트러스 높이 | 낮음(<1.0m) / 중간 / 높음(>2.0m) (B-2) |
| 생육 단계 | 초기 / 성기 / 후기 (과실 크기·색상 변동) |
| 밀집도 | 낮음 / 중간 / 높음 (A-4) |

### 6.3 반복 순회 촬영 — 같은 트러스를 다시 찍는다

2~3일 주기로 **동일 트러스를 반복 촬영**한다. 두 가지 이점이 있다.
1. 같은 과실의 숙성 진행 과정이 시계열로 남아, 6단계 경계 라벨의 근거가 생긴다.
2. 재순회 스케줄링 기능(PRD 5.1-6)의 실제 검증 데이터가 된다.

### 6.4 목표 규모 (단계별)

> 아래 수치는 문서화된 공식 권고치가 아니라 **본 과제의 계획 목표치**다. 실제 필요량은 7절 학습 실험에서 학습 곡선을 보고 조정한다.

| 단계 | 자체 촬영 이미지 | 관리 기준 | 목적 |
| :--- | :--- | :--- | :--- |
| A. 부트스트랩 | 1,500장 | 6단계 각 클래스 **인스턴스** 500개 이상 | 라벨링 지침 검증, 학습 파이프라인 구축 |
| B. 본 학습 | 5,000장 | 각 클래스 인스턴스 2,000개 이상 | KPI 목표 도달 시도 |
| C. 일반화 | 10,000장 (계절 2회차 + 온실 2곳 이상) | 예외 클래스 각 300개 이상 | 계절·온실 간 일반화 검증 |

**이미지 수보다 인스턴스 수로 관리한다.** 한 장에 과실이 10~30개 들어가므로 이미지 수는 실제 학습량을 반영하지 않는다.

### 6.5 롱테일 확보

`over_ripe`·`cracked`·`malformed`는 자연 발생률이 낮아 무작위 수집으로는 모이지 않는다. 재배 담당자와 협의해 **의도적으로 남겨둔 개체를 별도 촬영**하고, 부족분은 정상 과실 마스크에 균열·변형 텍스처를 합성해 보완한다(전처리 문서 4장의 예외 클래스 합성 증강).

## 7. 라벨링 정책

### 7.1 판정 기준을 물리적으로 고정한다

6단계 경계를 라벨러의 눈대중에 맡기면 정확도 목표는 의미를 잃는다. 다음을 강제한다.
- **표준 컬러차트를 인쇄해 촬영 프레임에 함께 넣는다.** 라벨러는 차트와 과실을 같은 이미지에서 비교한다.
- 경계가 애매한 개체는 `uncertain` 플래그를 달고 별도 검토 큐로 보낸다. 억지로 한 단계를 고르게 하면 라벨 노이즈가 그대로 모델에 학습된다.

### 7.2 라벨 품질을 측정한다

PRD는 숙성도 판별 정확도 90%를 목표로 하면서, 인접 단계 경계에서는 **숙련 인력 간 일치도(약 85~90%)가 상한선**임을 명시한다. 따라서 라벨 품질 자체가 정확도의 천장이다.
- 전체의 **10%를 이중 라벨링**하고 라벨러 간 일치도(Cohen's kappa)를 측정한다.
- 인접 단계 혼동(light_red ↔ red 등)을 별도 집계한다. 이 값이 목표 정확도보다 낮으면 모델 문제가 아니라 라벨 정의 문제다.

### 7.3 부분 라벨링을 금지한다

Ultralytics 문서는 부분 라벨링 데이터로도 학습은 가능하지만, 최선의 결과를 위해 각 이미지에서 대상 클래스의 **모든** 객체를 라벨링할 것을 권고한다(라벨이 없는 이미지는 학습에서 제외되어 손실에 기여하지 않는다). 잎에 반쯤 가려진 과실을 "애매해서" 빼면, 모델은 그 영역을 배경으로 학습한다. 가림 대응이 이 과제의 최상위 리스크인데 정확히 그 능력을 스스로 깎는 셈이다. 가려진 과실도 보이는 부분만 라벨링한다.

### 7.4 꼭지 라벨링 지침

꼭지는 가늘어 라벨러가 대충 그리기 쉽지만, 여기서 축 방향이 나오고 그것이 절단 정밀도 ±2mm를 결정한다.
- 과실과 붙는 지점부터 화방 주축(rachis)까지 **끊기지 않게** 그린다.
- 여러 과실의 꼭지가 겹쳐 보일 때는 각각 별도 인스턴스로 분리한다(합치면 축 추정이 무의미해진다).

## 8. 학습 전략

### 8.1 3단계 전이

```
1) Laboro Tomato baseline (exp-2.pt, 3단계·꼭지 없음)
      ↓  구조 클래스와 방울토마토 형상에 대한 표현 재사용
2) 자체 부트스트랩 데이터 1,500장 (12클래스) — 헤드 교체 후 fine-tune
      ↓
3) 자체 본 데이터 5,000장 + 계절 확장 — 전체 fine-tune
```

**클래스 수가 달라도 대부분의 가중치는 그대로 넘어온다.** 재초기화되는 것은 마지막 분류 컨볼루션뿐이고 백본·넥·공유 헤드는 전부 전이된다. 즉 6클래스 베이스라인에서 12클래스로 바꾸는 것이 "처음부터 다시"를 뜻하지 않는다.

전이학습이 실제로 사는 것은 최종 정확도가 아니라 **도달 시간**이다. 스크래치도 오래 돌리면 따라오지만, 그 시간이 곧 클라우드 비용이고 수확기 마감이다. 본 과제는 데이터 수집 자체가 생육기에 종속되므로(13절) 시간이 가장 비싼 자원이다.

**출발 가중치 선택** — 두 후보가 있고, 도메인이 더 가까운 쪽이 유리하다.

| 출발점 | 장점 | 판단 |
| :--- | :--- | :--- |
| `yolo26n-seg.pt` (COCO 사전학습) | 일반적인 시각 표현이 폭넓다 | 대조군으로 사용 |
| `exp-2.pt` (Laboro Tomato 학습) | **같은 작물**의 형상·질감·배경에 이미 적응돼 있다 | **주 후보** |

두 후보를 부트스트랩 단계에서 A/B로 비교하고, 이후 단계는 이긴 쪽으로 고정한다.

### 8.1.1 매핑 가능한 클래스는 분류 가중치를 이어받는다

3단계 → 6단계는 **세분화**이므로 일부 클래스는 개념이 그대로 대응된다. 대응되는 인덱스를 맞춰주면 그 분류 가중치를 물려받을 수 있다. 이것은 자동으로 되지 않으므로 직접 해야 한다.

| 베이스라인 클래스 | 신규 클래스 | 대응 |
| :--- | :--- | :--- |
| `l_green` | `green` | 개념 일치 — 이어받기 가능 |
| `l_fully_ripened` | `red` | 근사 대응 — 이어받기 가능 |
| `l_half_ripened` | `breaker` / `turning` / `pink` 중 다수 | **1:3 분화 — 1:1 매핑 불가, 재초기화** |
| `b_*` (일반 대과) | 없음 | 방울토마토 한정이므로 폐기 |

`half_ripened` 하나가 3개 단계로 쪼개지는 지점이 이번 재라벨링의 실질적 난이도다. 이 구간의 라벨 품질이 곧 숙성도 정확도 KPI를 결정한다.

> **주의**: 클래스 이름·인덱스 조정은 모델을 로드한 뒤 **메모리 상에서만** 수행한다(`model.names[idx] = ...`). `.pt` 파일 자체를 덮어쓰면 원본 가중치를 되돌릴 수 없다.

### 8.1.2 모델 크기는 n에서 시작한다

큰 모델은 용량이 큰 그릇이고, 데이터가 그 그릇을 채우지 못하면 남는 용량으로 학습 데이터를 **암기**한다. 부트스트랩 1,500장에서 `x`를 쓰면 과적합이 사실상 보장된다.

정석은 **n → 정체되면 s → 그다음 m**이다. 본 과제는 여기에 제약이 하나 더 붙는다 — Jetson Orin NX에서 비전 추론 5초 예산을 지켜야 하므로 크기 상향은 추론 시간 재측정을 전제로만 허용한다. **크기를 올렸는데 성능이 오르지 않으면 문제는 모델이 아니라 데이터다.**

### 8.2 분할 전략 — 무작위 분할을 금지한다

이것이 가장 흔하게 성능을 부풀리는 함정이다. 같은 트러스를 2~3일 주기로 반복 촬영하면 **거의 동일한 과실 이미지가 여러 장** 생긴다. 무작위로 분할하면 train과 val에 같은 과실이 나뉘어 들어가 검증 점수가 실제보다 크게 높아진다.

| 분할 | 기준 | 목적 |
| :--- | :--- | :--- |
| train / val | **트러스 ID 그룹 분할** — 같은 트러스는 한쪽에만 | 개체 누출 차단 |
| test | **별도 촬영일 + 별도 구역** | 시점·구역 일반화 |
| 최종 홀드아웃 | **별도 온실 + 별도 계절** | 실배포 조건 근사. 이 점수만 대외 성능으로 인정 |

### 8.3 증강 정책 — 전처리 파이프라인과 정합시킨다

증강은 자유롭게 켜는 것이 아니다. 숙성도 라벨의 근거가 **색상**이므로, 색상을 왜곡하는 증강은 라벨과 이미지를 불일치시킨다.

| 증강 | 설정 | 근거 |
| :--- | :--- | :--- |
| `hsv_h` (색상 지터) | **0.0 — 금지** | 숙성 단계 라벨의 근거를 파괴한다. light_red를 red로 밀어버리면 정답이 틀린 데이터가 된다 |
| `hsv_s` (채도) | 매우 약하게 | 과도하면 발색 판정에 영향 |
| `hsv_v` (명도) | 적극 사용 | 시간대·그림자 변동 대응. 전처리의 조도 정규화와 목적이 일치 |
| `copy_paste` | **적극 사용** (`mode="flip"`) | 인스턴스 세그멘테이션 전용 증강. 잎·과실 인스턴스를 합성해 **가림과 밀집도를 인위적으로 늘린다** — 최상위 리스크(Occlusion)와 A-4(밀집도)에 직접 대응 |
| `mosaic` | 사용, 학습 후반 종료(`close_mosaic`) | 소형 객체 다양성 확보 |
| 기하 변환(flip·scale·rotate) | 사용 | 트러스 배치 변동 대응 |
| 합성 잎 가림 오버레이 | 오프라인 전처리로 별도 생성 | Blender 절차적 식물 생성 활용 |

### 8.4 소형 객체 대응 — `scale`과 `multi_scale`을 구분한다

지름 15~30mm 과실은 400mm 거리에서 약 14~30px이다. 640×640 입력에서 이는 매우 작은 객체다.
- 1차: `imgsz=640` 기준선 학습 후, `imgsz=960`/`1280` 비교. 정확도 향상분과 추론 시간 증가분을 함께 기록한다.
- 2차: 향상폭이 부족하면 트러스 영역 **타일링 추론**을 검토한다(전체 프레임을 겹치는 타일로 나눠 추론).
- YOLO26의 ProgLoss + STAL이 이 조건에서 이득을 주는지 YOLO11-seg와 A/B 비교로 확인한다.

두 인자가 이름이 비슷해 혼동되지만 건드리는 층위가 다르다.

| | `scale` | `multi_scale` |
| :--- | :--- | :--- |
| 바꾸는 것 | 이미지 **내용**의 배율 | **입력 텐서 크기** |
| 최종 입력 | 항상 640 고정 | 480~800 변동 |
| 계층 | 증강(augmentation) | 샘플링 |
| 비용 | 거의 없음 | 느려짐 |

**본 과제의 결정**: `scale`은 사용하고 **`multi_scale`은 사용하지 않는다.** 배포 입력이 640×640 stretch 단일 규격으로 고정되어 있기 때문이다(`inference_config.json`). 배포 해상도가 하나면 `multi_scale`은 학습 시간만 늘리고 얻는 것이 없다.

### 8.5 조기 종료와 옵티마이저 — 기본값을 그대로 쓰면 안 되는 두 곳

**`patience` 기본값 100은 파인튜닝에 너무 크다.** 사전학습 모델은 원래 빨리 수렴해서 30에폭 부근에 최고점을 찍고 남은 에폭을 태우는 일이 흔하다. 파인튜닝에서는 **10~20**으로 낮춘다. `epochs=300`은 상한일 뿐이고 실제 종료는 `patience`가 결정한다.

**`optimizer=auto`는 `lr0`를 덮어쓴다.** 이것이 가장 많이 걸리는 함정이다. `auto`는 총 반복 횟수(`epochs × 이미지수 / batch`)를 계산해 옵티마이저와 **학습률까지 스스로 정하므로**, 사용자가 준 `lr0`가 조용히 무시된다. "학습률을 낮췄는데 결과가 똑같다"의 원인이 대부분 이것이다.

| 상황 | 설정 |
| :--- | :--- |
| 학습률을 건드리지 않는 기본 학습 | `optimizer` 생략(auto) — YOLO26은 MuSGD 계열이 선택된다 |
| **`lr0`를 직접 제어해야 할 때** (2단계 파인튜닝 Stage 2 등) | **`optimizer`를 반드시 명시** |

`warmup_epochs`는 시작 구간, `lrf`는 종료 구간을 담당한다. 파인튜닝에서 웜업이 특히 중요한 이유는 **잘 학습된 가중치로 시작**하기 때문이다 — 첫 배치부터 큰 학습률로 때리면 그 가중치가 흐트러진다. 파인튜닝이라고 웜업을 0으로 줄이지 말고 **기본값 3을 유지**한다.

### 8.6 레이어 프리징 — 데이터 양과 도메인 유사도, 두 축으로 결정한다

`freeze=N`은 레이어 0~(N−1)을 얼린다. YOLO26 백본은 레이어 0~10이므로 `freeze=10`은 마지막 C2PSA 블록을 학습 상태로 남기고, 백본을 완전히 동결하려면 `freeze=11`이다.

두 축은 서로 독립이다. **데이터 양**은 "얼마나 학습시켜도 되는가"를 정하고, **도메인 유사도**는 "기존 특징이 쓸모 있는가"를 정한다.

| 데이터 | 도메인 | 권장 | 근거 |
| :--- | :--- | :--- | :--- |
| 대규모 | 유사 | `freeze=None` | 데이터가 풍부해 전 레이어 재학습이 안전 |
| 소규모 | 유사 | `freeze=10` | 백본 특징 유지 + 학습 파라미터 대폭 경감 |
| 극소 | — | `freeze=23` | 탐지 헤드만 조정해 과적합 방지 |
| — | 매우 다름 | `freeze=None` | 백본 특징이 무용하므로 깊은 곳까지 수정 |

**본 과제의 적용**: 온실 토마토는 자연 이미지이므로 COCO와 **유사 도메인**이고, 베이스라인에서 출발하면 더 가깝다. 따라서 데이터 양이 결정 인자가 된다.

| 단계 | 데이터 | 권장 freeze |
| :--- | :--- | :--- |
| 부트스트랩 | 1,500장 (소규모) | `freeze=10` |
| 본 학습 | 5,000장 | `freeze=None`으로 완화 후 비교 |
| 일반화 | 10,000장 | `freeze=None` |

### 8.7 2단계 파인튜닝 — 시도하되 기대하지 않는다

데이터도 적고 도메인도 먼 최악의 경우에 쓰는 기법이다. 헤드가 아직 아무것도 모르는 상태에서 전체를 한 번에 학습시키면, 헤드가 뿜는 엉뚱한 그래디언트가 백본까지 흘러 멀쩡한 백본을 망가뜨린다.

```
Stage 1  freeze=11 (백본 동결)          → 헤드를 진정시키는 단계. 높은 성능을 기대하지 않는다
Stage 2  freeze=None + lr0=0.001 이하   → 백본까지 도메인에 맞추는 단계
         (lr0을 주려면 optimizer 명시 — 8.5절)
```

**본 과제에서의 판단**: 도메인이 COCO와 크게 다르지 않으므로 2단계가 필수는 아니다. 다만 클래스가 6→12로 크게 바뀌고 부트스트랩 데이터가 적으므로 **부트스트랩 단계에서 단일 단계와 A/B 비교할 가치는 있다.** 2단계는 항상 이기는 마법이 아니라 도메인 격차가 클 때 학습 불안정을 줄이는 선택지이며, 데이터·하드웨어 조건에 따라 단일 단계가 이길 수도 있다.

### 8.8 클래스 불균형 — 예외 클래스는 발생률 자체가 낮다

`over_ripe`·`cracked`·`malformed`는 롱테일이다(6.5절). mAP는 클래스별 평균이므로 희귀 클래스 하나가 전체 점수를 크게 깎는다.

`cls_pw`로 클래스 가중치를 조정한다. 가중치는 `(1/클래스 개수)^cls_pw`로 계산되어 평균이 1이 되도록 정규화된다. **0.25에서 시작**하고, 그래도 희귀 클래스가 잡히지 않으면 1.0까지 올린다.

### 8.9 처리량 최적화 — 실험 횟수가 곧 최종 성능이다

학습이 3시간 걸리면 하루에 실험을 3번 하고 40분이면 12번 한다. 속도 최적화는 편의가 아니라 **성능을 사는 일**이다.

| 인자 | 설정 | 주의 |
| :--- | :--- | :--- |
| `batch` | VRAM이 허락하는 최대치. 처음 만지는 GPU는 **`batch=-1`**(자동 산정)로 시작 | 수동으로 찾을 때는 OOM이 날 때까지 올린 뒤 한 단계 내린다 |
| `cache` | 검토 — 단 RGB+Depth라 용량이 크므로 RAM 여유 확인 | **첫 에폭에는 효과가 없고 오히려 느리다.** 2에폭째부터 빨라지므로 짧은 벤치마크로 판단하면 효과를 못 본다 |
| `amp` | 기본값 `True` **유지** | 끄면 느려지고 VRAM도 더 쓰는데 정확도 이득이 없다 |
| `fraction` | 설정 검증용으로만 사용 | **절대 성능 판단용이 아니다.** 후보 A/B의 순위를 보는 정도로만 쓴다 |

`fraction`이 특히 유용한 이유: 자체 촬영 데이터는 귀하고 학습 시간은 길다. `data.yaml` 경로 오타로 val이 비어 있는 상태로 몇 시간을 날리는 사고를 `fraction=0.1` 리허설로 미리 막는다.

### 8.10 학습 설정 출발점

```python
from ultralytics import YOLO

# 도메인이 더 가까운 베이스라인에서 출발(8.1절). COCO 사전학습과 A/B 비교한다.
model = YOLO("exp-2.pt")

model.train(
    data="cherry_tomato.yaml",   # 12클래스 (5절)
    epochs=300,                  # 상한. 실제 종료는 patience가 결정한다
    patience=15,                 # 기본 100은 파인튜닝에 과도 (8.5절)
    imgsz=640,                   # 배포 규격과 일치. 상향은 별도 실험으로 (8.4절)
    batch=-1,                    # VRAM에 맞춰 자동 산정 (8.9절)
    device=0,
    freeze=10,                   # 소규모 + 유사 도메인 (8.6절)
    cls_pw=0.25,                 # 예외 클래스 롱테일 보정 (8.8절)

    # 증강 — 전처리 파이프라인과 정합 (8.3절)
    hsv_h=0.0,                   # 색상 지터 금지: 숙성 라벨의 근거를 파괴한다
    hsv_s=0.2,
    hsv_v=0.5,
    copy_paste=0.4,              # 가림·밀집 합성
    close_mosaic=30,
    multi_scale=False,           # 배포 해상도가 단일이므로 불필요 (8.4절)

    # optimizer 미지정(auto). lr0를 직접 주려면 반드시 명시해야 한다 (8.5절)
)
```

에폭·배치는 출발점이며 학습 곡선과 val 지표를 보고 조정한다. **설정 변경은 한 번에 하나씩** 바꿔 원인을 추적할 수 있게 한다.

## 9. 평가 프로토콜

### 9.1 mAP만 보면 안 되는 이유

mAP는 모든 클래스 오분류를 동등하게 취급한다. 그러나 이 과제에서 오분류의 비용은 **비대칭**이다.

| 오분류 방향 | 결과 | 비용 |
| :--- | :--- | :--- |
| 미숙과 → 완숙으로 판정 | 익지 않은 과실을 수확 | **높음** — 상품가치 손실 + 되돌릴 수 없음 |
| 완숙과 → 미숙으로 판정 | 수확을 건너뜀 | 중간 — 차기 순회에서 회수 가능 |
| 인접 단계 혼동 (light_red ↔ red) | 등급 편차 | 낮음 |
| 꼭지 미검출 | Stage B 전량 스킵 | **높음** — 수확 0건 |

따라서 mAP와 별도로 아래를 필수 지표로 관리한다.

### 9.2 PRD KPI로 환산되는 지표

| 모델 지표 | 대응 PRD KPI | 측정 방법 |
| :--- | :--- | :--- |
| 6×6 숙성 혼동행렬 | 숙성도 판별 정확도 90% | 인접 단계 혼동과 비인접 혼동을 분리 집계 |
| 과실 클래스 recall | 1회 순회 미탐지율 15% 이하 | 가림 비율 구간별(0~30%/30~50%/50%+) 분해 |
| `pedicel` recall + 축 각도 오차 | 파지·절단 포즈 추정 성공률 85% | 마스크에서 유도한 축 방향과 정답 축의 각도 차(deg) |
| 예외 클래스 precision | 손상률 5% 이하 | 열과·기형과를 정상으로 놓친 비율 |
| 추론 시간(Jetson 실측) | 비전 추론 5초 예산 | Edge 실기 측정. 데스크톱 GPU 수치는 무효 |

### 9.3 파이프라인 결합 평가

모델 단독 지표가 좋아도 파이프라인 최종 산출이 나쁠 수 있다. 학습된 모델을 실제 `harvest_pipeline`에 주입해 **수확 대상 산출 수**를 측정하는 것이 최종 검증이다. 규칙 기반 베이스라인(`ClassicalColorSegmentationModel`)과 동일 프레임에서 비교하면 개선폭이 정량화된다.

## 10. 학습 중 자주 겪는 문제와 진단 순서

실험 횟수가 성능을 결정하므로(8.9절), 문제 진단에 쓰는 시간을 줄이는 것도 성능 관리의 일부다. **확인이 빠른 것부터** 보는 순서를 고정해 둔다.

### 10.1 모델이 아무것도 예측하지 못한다

| 순서 | 확인 | 이유 |
| :--- | :--- | :--- |
| 1 | **`conf` 임계값을 0.1로 낮춰 본다** | 가장 빠르다. 뭐라도 나오면 모델은 살아 있고 성능이 부족한 것이므로 완전히 다른 문제다 |
| 2 | **데이터 경로 / 라벨 매칭** | 가장 악질이다 — **에러가 나지 않는다.** 라벨을 0개 찾고 그대로 조용히 학습이 끝난다 |
| 3 | 클래스 인덱스·`nc` 일치 | `data.yaml`의 클래스 수와 라벨 파일의 인덱스 범위가 어긋나면 조용히 망가진다 |

경로 불일치가 조용히 실패하기 때문에 **학습 전에 val을 한 번 돌려 라벨이 실제로 읽히는지 확인하는 것을 게이트로 넣는다.** 본 과제는 자체 데이터셋을 새로 구축하므로 이 위험이 특히 크다(NDJSON → YOLO 형식 변환 단계가 끼어 있다).

### 10.2 mAP가 일찍 정체된다

첫 반응이 "에폭을 늘려볼까"인 경우가 많지만 **그건 거의 답이 아니다.** 이미 평평해진 곡선은 더 돌려도 평평하다. 원인은 보통 아래 중 하나다.

| 원인 | 처방 |
| :--- | :--- |
| 클래스 불균형 (예외 클래스 롱테일) | `cls_pw` 조정 (8.8절) |
| 데이터 양·다양성 부족 | 수집 조건 매트릭스의 빈 칸을 채운다 (6.2절) |
| 모델 용량 부족 | `n` → `s` 상향. 단 추론 시간 재측정 전제 (8.1.2절) |
| 라벨 품질 한계 | 라벨러 간 일치도를 먼저 측정한다 — 이 값이 목표보다 낮으면 모델 문제가 아니다 (7.2절) |

### 10.3 치명적 망각 (Catastrophic Forgetting)

새 데이터에 특정 클래스가 없으면 모델은 "그 개념은 이제 필요 없다"로 학습한다. 모델이 배신한 것이 아니라 그렇게 가르친 것이다.

**본 과제에서는 이것이 대부분 의도된 동작이다.** 베이스라인의 `b_*`(일반 대과) 클래스를 버리는 것은 방울토마토 한정 시스템이므로 정상이다. 다만 향후 대과 품종까지 지원하려면 주의해야 한다 — **완벽한 회피 방법은 하나뿐이며, 이전 클래스와 새 클래스 이미지를 병합한 종합 데이터셋으로 학습하는 것이다.** 나머지 기법은 모두 완화책이고 망각을 없애지 못하고 늦출 뿐이다.

## 11. Edge 배포 계획

| 단계 | 내용 | 확인 사항 |
| :--- | :--- | :--- |
| 1 | TensorRT 엔진 export | Jetson Orin NX의 JetPack/TensorRT 버전에 맞춰 **기기에서 직접** 빌드 |
| 2 | FP16 → INT8 양자화 비교 | 양자화 후 **숙성 혼동행렬을 다시 측정**한다. 색상 미세 구분이 양자화에 민감할 수 있다 |
| 3 | 추론 시간 실측 | 5초 예산 대비 여유 확인. 파이프라인은 워커 스레드 타임아웃으로 감시하되 파이썬 스레드는 강제 종료가 불가하므로 예산 초과 자체를 막아야 한다 |
| 4 | 전처리 규격 일치 | 학습 시 resize 방식(stretch)과 배포 시 방식이 달라지면 정확도가 조용히 떨어진다. 현 `inference_config.json`은 stretch·1/255·RGB로 고정되어 있다 |

> **확인 필요 사항**: 현재 Roboflow 경유 export의 `inference_config.json`은 `post_processing: {"type": "nms"}`로 되어 있다. YOLO26은 NMS-free 설계가 강점인데 내보내기 경로에서 NMS가 다시 붙은 형태다. Ultralytics 공식 export 경로로 재확인해 불필요한 후처리 지연을 제거할 수 있는지 검토한다.

## 12. MLOps 재학습 루프

파이프라인에 이미 실패 케이스 수집 기능이 있으므로 이를 학습 루프에 연결한다.

```
운영 중 발생 → 자동 수집 큐 → 라벨링 → 데이터셋 증분 → 재학습 → 회귀 평가 → 배포
```

수집 대상: `SKIP_LOW_CONFIDENCE`(신뢰도 미달), `SKIP_NO_PEDICEL`(꼭지 미검출), 손상 발생 케이스, 48시간 후 표본 검사에서 발견된 지연성 내상.

**재학습 트리거**: ① 시즌/품종 전환 ② 신규 온실 구역 투입 ③ 특정 스킵 사유가 임계치 초과 ④ 수집 큐가 일정 규모 도달.

**회귀 평가 게이트**: 재학습 모델은 이전 모델의 홀드아웃 점수를 하회하면 배포하지 않는다. MLflow로 버전·지표·데이터셋 스냅샷(DVC)을 함께 기록한다.

## 13. 일정 및 산출물

| 단계 | 기간 | 주요 활동 | 산출물 | 통과 기준 |
| :--- | :--- | :--- | :--- | :--- |
| **0. 준비** | 2주 | 클래스 정의 확정, 라벨링 지침 작성, 촬영 장비·컬러차트 준비 | 라벨링 지침서, 촬영 프로토콜 | 지침대로 20장 시범 라벨링 후 라벨러 간 일치도 확인 |
| **1. 부트스트랩** | 4~6주 | 자체 1,500장 촬영·라벨링, 베이스라인 전이 학습 | 데이터셋 v1, 모델 v1 | 꼭지 recall이 유의미하게 나옴(Stage B가 동작함) |
| **2. 본 학습** | 8~10주 | 5,000장 확장, 증강·해상도 실험, 하이퍼파라미터 조정 | 데이터셋 v2, 모델 v2, 실험 기록 | 숙성 정확도·미탐지율이 KPI 목표에 접근 |
| **3. 일반화** | 6~8주 | 계절 2회차·타 온실 수집, 홀드아웃 평가 | 데이터셋 v3, 모델 v3 | 별도 온실 홀드아웃에서 성능 유지 |
| **4. Edge 최적화** | 3~4주 | TensorRT·양자화, 실기 추론 시간 측정 | 배포 엔진, 성능 리포트 | 5초 예산 내 + 양자화 후 정확도 유지 |

이 일정은 PRD 7장 로드맵의 MVP(4~6개월)·Phase 1(4~6개월)과 병행된다. 특히 **데이터 수집은 작물 생육기에 종속**되므로(PRD 5.3 가정 사항) 수확기를 놓치면 다음 재배 주기까지 지연된다 — 이것이 일정상 가장 큰 제약이다.

| **소형 객체 정확도 한계** | 미탐지율 목표 미달 | 해상도 상향·타일링 검토, 필요 시 `s` 크기로 상향(추론 시간 재측정 전제) |
| **양자화로 색상 구분력 저하** | 숙성 판별 정확도 저하 | INT8 적용 전후 혼동행렬 비교, 미달 시 FP16 유지 |
| **계절·품종 변동에 따른 성능 드리프트** | 운영 중 정확도 하락 | 시즌 전환 재학습 트리거, 스킵 사유 모니터링 |

## 15. 요약

1. **세그멘테이션이 필수**다. 꼭지 마스크 없이는 파이프라인이 한 과실도 수확하지 못한다.
2. **공개 데이터셋만으로는 불가능**하다. Laboro Tomato는 숙성 3단계이고 꼭지 클래스가 없어, PRD의 6단계 요구와 Stage B 요구를 둘 다 만족하지 못한다. 베이스라인 출발점으로만 쓴다.
3. **자체 수집이 이 계획의 본체**다. RGB뿐 아니라 Depth·내부 파라미터·메타데이터를 함께 저장해야 하며, 같은 트러스를 반복 촬영해 숙성 진행을 시계열로 남긴다.
4. **라벨 품질이 정확도의 천장**이다. 컬러차트로 기준을 물리적으로 고정하고 일치도를 측정한다.
5. **무작위 분할을 금지**한다. 트러스 ID 기준 그룹 분할과 별도 온실 홀드아웃만이 실제 성능을 말해준다.
6. **증강은 전처리 파이프라인과 정합**해야 한다. 색상 지터는 금지하고, `copy_paste`로 가림·밀집을 인위적으로 늘린다.
7. **최종 검증은 모델 단독 지표가 아니라 파이프라인 결합 산출**이다.
