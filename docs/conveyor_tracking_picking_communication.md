# [통신] 지연 보상 X/Z 컨베이어 트래킹 픽킹 연구 셀 — 통신 구조

> **문서 성격**: [conveyor_tracking_picking_prd.md](./conveyor_tracking_picking_prd.md)에 흩어져 있는 통신 요구(§1.3 시각·클록, §4 구성, §6 안전)를 하나의 통신 규약으로 전개한 문서다. 부품과 전원은 [conveyor_tracking_picking_hardware_bom.md](./conveyor_tracking_picking_hardware_bom.md)를 참조한다.
>
> **⚠ 읽는 법**
> - **[PRD]** — PRD가 명시한 요구. 절 번호를 함께 적었다. 바꾸려면 PRD를 먼저 고쳐야 한다.
> - **[제안]** — PRD에 없는 값. PRD 제약에서 역산한 설계안이며 구현 시 실측으로 확정한다.
>
> PRD는 "UART", "heartbeat 100 ms", "30회 교환" 같은 **요구**는 정하지만 프레임 형식·보드레이트·메시지 종류는 정하지 않는다. 그 층이 이 문서다.
>
> **개정 이력**: v1 — 최초 작성.

## 1. 통신 지도

```
                    ┌──────────────────────────────┐
   [글로벌셔터 카메라]─CSI/USB─▶│                              │
                              │   상위 컴퓨터 (Pi)            │
                              │   검출 · 예측 · 로그          │
                              │   시계 C_Pi                   │
                              └───┬──────────────────┬────────┘
                                  │ UART-A           │ UART-B / USB-CDC
                                  │ 명령·하트비트·시각교환  │ 로그 벌크 (제어와 분리)
                                  ▼                  ▼
                              ┌──────────────────────────────┐
                              │   실시간 제어 MCU (ESP32)      │
                              │   안전 상태 기계 소유          │
                              │   시계 C_ESP                  │
                              └──┬────┬────┬────┬────┬───┬────┘
                                 │    │    │    │    │   │
        인코더 A/B (PCNT) ────────┘    │    │    │    │   │
        IR ×2 (GPIO 인터럽트) ─────────┘    │    │    │   │
        압력 (ADC1, 100~200 Hz) ───────────┘    │    │   │
        리미트 ×4 · E-stop 보조 (GPIO, NC) ─────┘    │   │
        STEP/DIR ×2 · 서보 PWM ──────────────────────┘   │
        밸브 · 펌프 · 동기 LED (GPIO→MOSFET) ─────────────┘

   [기준 영상 장치] ── 연결 없음 (독립) ── 동기 LED를 화면으로만 관측
```

**[PRD §3.1]** 기준 영상 장치는 제어계와 **분리**되어야 한다. 따라서 이 장치로 가는 통신 링크는 존재하지 않는다. 로그와의 시각 정합은 ESP32가 켜는 **동기 LED를 영상에 찍는 방식**으로만 이뤄진다 — 전선이 아니라 빛으로 동기한다.

## 2. 핵심 설계 결정 — 명령은 시각이 아니라 인코더 카운트로 보낸다

**[PRD §1.3]** 은 두 가지를 동시에 요구한다.

1. 클록 매핑은 **사건 상관과 사후 지연 측정에만** 쓰며 "ESP32의 제어 권한·모션 명령·안전 상태를 바꾸지 않는다"
2. 원시 Pi·ESP32 시각을 **직접 빼는 것은 금지**

명령에 "이 시각에 접촉하라"를 담으면 이 두 요구를 지킬 수 없다. ESP32가 Pi 시각을 해석하려면 매핑이 제어 경로에 들어와야 하고, 매핑이 무효화되는 순간 제어가 함께 무너진다.

> **[제안] 그래서 명령의 목표를 `encoder_count_contact_target`으로 표현한다.**
>
> Pi는 예측 결과를 **인코더 카운트**로 변환해 보낸다. ESP32는 자기 인코더 카운터만 보고 그 값에 도달할 때 동작한다. **제어 경로에 두 시계의 매핑이 전혀 등장하지 않는다.**

이 선택의 결과는 다음과 같다.

| 항목 | 효과 |
| :--- | :--- |
| 클록 매핑 | 사후 분석 전용이 된다 — [PRD §1.3] 준수가 구조적으로 보장됨 |
| 매핑 무효화 시 | 분석은 무효가 되지만 **제어는 영향 없음**. 새 픽 금지는 별도 정책으로 처리 |
| 벨트 속도 변동 | 카운트 기준이라 자동으로 흡수됨 |
| 전송 지터 | 명령이 조금 늦게 도착해도 목표 카운트는 그대로. 늦으면 ESP32가 `NO_PICK_MOTION_LATE`로 자체 판정 |

`t_contact_pred_pi`(Pi 시각)는 여전히 **기록**하지만 명령에는 넣지 않는다. 예측의 근거로 로그에 남고, 사후에 실제 접촉 시각과 비교되는 값이다.

## 3. UART-A — 명령·하트비트·시각교환 링크

### 3.1 물리 계층 [제안]

| 항목 | 값 | 근거 |
| :--- | :--- | :--- |
| 방식 | UART, 8N1, 흐름제어 없음 | 단순·결정론적. 지터가 낮다 |
| 전압 | 양측 3.3 V | Pi GPIO UART와 ESP32 모두 3.3 V — **레벨 시프터 불필요** |
| 보드레이트 | **921,600 bps** | 24바이트 프레임 기준 전송 약 0.26 ms. 115,200이면 약 2.1 ms로 지연 예산의 상당 부분을 먹는다 |
| Pi 측 포트 | **PL011 (`ttyAMA0`)** | 아래 주의 참조 |

> **⚠ Pi의 mini UART(`ttyS0`)를 쓰지 않는다 [제안]**
> mini UART는 보드레이트가 **코어 클록에 종속**된다. CPU 주파수 스케일링이 일어나면 실효 보드레이트가 흔들려 전송 시간이 변한다. 지연을 ms 단위로 재는 셀에서 이는 조용한 오차원이다. PL011로 고정하고, 부팅 설정에서 블루투스를 UART에서 떼어낸다.

### 3.2 프레임 형식 [제안]

```
+------+------+------+------+-----------+--------+
| SOF0 | SOF1 | TYPE | SEQ  |  PAYLOAD  | CRC16  |
| 0xA5 | 0x5A | 1B   | 2B   |  고정 길이  | 2B     |
+------+------+------+------+-----------+--------+
```

- **길이 필드가 없다.** `TYPE`마다 페이로드 길이를 **고정**했다. 프레임 크기가 상수여야 전송 시간이 상수가 되고, 그래야 `t_cmd_tx_pi → t_cmd_rx_esp` 구간이 예측 가능해진다.
- **SEQ**: 방향별 롤링 카운터. 유실·중복·순서 뒤바뀜을 수신 측이 판정한다.
- **CRC16-CCITT**: `TYPE`부터 `PAYLOAD` 끝까지. 실패 프레임은 **버리고 카운트만 한다 — 절대 동작하지 않는다.**
- 프레임 중간에서 타임아웃되면 `SOF` 재동기부터 다시 시작한다.

### 3.3 메시지 종류 [제안]

**Pi → ESP32**

| TYPE | 이름 | 주기·시점 | 페이로드 요지 |
| :--- | :--- | :--- | :--- |
| `0x10` | `HEARTBEAT` | **100 ms** [PRD §6] | `trial_id` 또는 keepalive, Pi 시퀀스 |
| `0x11` | `CLOCK_PING` | 블록 시작 30회 / 5분마다 10회 [PRD §1.3] | 교환 번호 |
| `0x20` | `PICK_PLAN` | 적격 후보 확정 시 1회 | `command_id`, `trial_id`, `x_cmd`, **`encoder_count_contact_target`**, 접촉 창 폭 |
| `0x21` | `ABORT` | 즉시 | `command_id` |
| `0x30` | `CONFIG_SET` | **블록 시작에만** [PRD §6] | 가드 임계값 일괄, 설정 해시 |

**ESP32 → Pi**

| TYPE | 이름 | 시점 | 페이로드 요지 |
| :--- | :--- | :--- | :--- |
| `0x91` | `CLOCK_PONG` | `CLOCK_PING` 수신 즉시 | `e_rx`, `e_tx` **둘 다** [PRD §1.3] |
| `0xA0` | `ACK_X_START` | X축 첫 유효 스텝 직후 | `command_id`, `t_x_start_esp` |
| `0xB0` | `STATE` | 상태 전이 시 | from/to 상태, **촉발 원인** |
| `0xB1` | `FAULT` | 즉시 | fault 코드, 원인 |

> **[PRD §1.3] `ACK`는 비동기 진단값이다.** `L_k` 계산이나 접촉 예측에 사용하지 않는다. ACK가 유실되어도, 물리 X 기동의 매핑이 유효하면 예측 표본을 무효화하지 않는다. ACK는 **귀환 전송 지연을 보는 용도**다.

### 3.4 로그를 이 링크에 태우지 않는 이유 [제안] — 중요

**[PRD §1.3]** 은 `t_cmd_tx_pi`를 "명령을 UART에 기록한 시각"으로 정의한다. 그런데 리눅스에서 UART 쓰기는 **커널 버퍼에 넣는 동작**이지 전선에 비트가 나가는 순간이 아니다.

이 링크에 로그 벌크가 섞여 있으면 이런 일이 벌어진다.

```
로그 200바이트가 큐에 대기 중  →  Pi가 명령을 write()  →  t_cmd_tx_pi 기록됨
                              →  실제 송신은 로그가 다 빠진 뒤 시작 (+2 ms)
                              →  L_k 가 조용히 2 ms 부풀려짐
```

**측정 대상이 측정 도구에 의해 오염된다.** 그래서 다음을 규칙으로 둔다.

- **UART-A에는 명령·하트비트·시각교환만 흐른다.** 이 세 종류는 모두 짧고 고정 길이다.
- **로그·이벤트 벌크는 UART-B 또는 USB-CDC 등 별도 경로로 보낸다.**
- 명령 송신 직전 TX 큐가 비어 있음을 확인한다. 비어 있지 않으면 그 시도를 `INVALID_TIMESTAMP`로 표시한다.

## 4. 시각 교환 절차

**[PRD §1.3]** 의 요구를 프로토콜로 옮기면 다음과 같다.

```
Pi                                    ESP32
 │  p_send 기록 (write 직전)
 ├──── CLOCK_PING(n) ──────────────────▶
 │                                      e_rx 기록 (프레임 완전 수신)
 │                                      e_tx 기록 (응답 write 직전)
 ◀──── CLOCK_PONG(n, e_rx, e_tx) ───────┤
 │  p_rx 기록 (프레임 완전 수신)
```

| 항목 | 값 | 근거 |
| :--- | :--- | :--- |
| 블록 시작 | **30회, 1초 이상에 걸쳐** | [PRD §1.3] |
| 재확인 | **5분마다 10회** | [PRD §1.3] |
| 적합 | `map_esp_to_pi(e) = a·e + b`, 중간시각 쌍으로 | [PRD §1.3] |
| 수락 조건 | 절대 residual **p95 ≤ 2 ms, 최대 ≤ 5 ms** | [PRD §1.3] |
| 보존 | `p_send`, `e_rx`, `e_tx`, `p_rx` **네 값 전부** + `a`, `b`, residual, mapping ID | [PRD §1.3] |

중간시각은 Pi 쪽 `(p_send + p_rx) / 2`, ESP32 쪽 `(e_rx + e_tx) / 2`로 잡는다. 왕복이 대칭이라는 가정이 들어가므로, **교환은 링크가 한산할 때만 수행한다** — 3.4절의 링크 분리가 여기서도 필요하다.

**매핑이 수락되지 않으면**: [PRD §1.3]에 따라 마지막 수락 이후 시도를 `INVALID_CLOCK_MAPPING`으로 무효화하고 새 픽을 금지한다. 다만 2절의 설계 덕분에 **이미 진행 중인 동작의 안전성은 매핑과 무관하다** — 매핑은 분석용이기 때문이다.

## 5. 하트비트와 통신 상실

**[PRD §6]** 이 정한 반응을 그대로 옮긴다.

| 항목 | 값 |
| :--- | :--- |
| Pi 송신 주기 | **100 ms** — 유효 `trial_id` 또는 keepalive |
| ESP32 판정 | 마지막 유효 하트비트 후 **300 ms** 경과 시 |
| `READY`·`TRACK` | 새 픽 금지 후 `RECOVER` |
| `ARMED`·`PICK`·`VERIFY`·`RECOVER` | **즉시 `FAULT_STOP`**, 모션 취소, 진공 해제 |

300 ms는 하트비트 3회분이다. 단발 유실로 정지하지 않으면서도 링크 단절은 확실히 잡는 값이다 [제안: 근거 해석].

> **[PRD §6] Pi는 이 반응을 우회할 수 없다.** 하트비트를 보내는 것 외에 ESP32의 판정을 늦추거나 취소하는 메시지는 프로토콜에 **정의하지 않는다.** 그런 메시지가 존재하면 안전 소유권이 실질적으로 Pi로 넘어간다.

## 6. 센서·액추에이터 인터페이스

모두 ESP32에 직결된다. 중간에 버스 확장기나 네트워크를 두지 않는다.

| 대상 | 인터페이스 | 처리 방식 | 근거 |
| :--- | :--- | :--- | :--- |
| 컨베이어 인코더 | 쿼드러처 A/B | **하드웨어 펄스 카운터(PCNT)** — 소프트웨어 인터럽트로 세지 않는다 | [PRD §6] 10 ms 표본 이상 판정 |
| IR 진입 · IR 게이트 | 디지털 GPIO | 엣지 인터럽트, 인터럽트 안에서 **카운터 값만 래치** | [PRD §4] 진입 태그 |
| 압력 센서 | 아날로그 → **ADC1** | 타이머 기반 **100~200 Hz** 고정 주기 | [PRD §6] 200 ms 창 / 50 ms 부재 판정 |
| 리미트 ×4 | 디지털 GPIO, **NC** | 단선 = 안전 측 동작 | [PRD §4] 물리 제한 |
| E-stop | 전원 물리 차단 + GPIO 보조 접점 | **신호가 아니라 전원을 끊는다** | [PRD §6] |
| X·Z 스테퍼 | STEP / DIR 펄스 | 하드웨어 타이머 기반 펄스 생성 | [PRD §4] |
| 드라이버 설정 | 드라이버 UART | **부팅 시 1회만.** 모션 중 설정 트랜잭션 금지 | [제안] 스텝 타이밍 간섭 방지 |
| 계량 게이트 서보 | PWM (LEDC) | `T_release` 주기 구동 | [PRD §2.3] |
| 밸브 · 펌프 | GPIO → MOSFET | 밸브는 **비여자 = 대기 개방** | [PRD §6] 진공 해제 요구 |
| 동기 LED | GPIO | 기준 영상과의 유일한 시각 접점 | [PRD §3.1] |

> **ADC2를 쓰지 않는다 [제안]**: ESP32의 ADC2는 WiFi와 자원을 공유해 WiFi 활성 시 읽기가 실패할 수 있다. 압력은 안전 판정 입력이므로 반드시 **ADC1**에 둔다.
>
> **인터럽트 안에서 무거운 일을 하지 않는다 [제안]**: IR 엣지에서 할 일은 인코더 카운트와 타임스탬프를 래치하는 것뿐이다. 판정과 로깅은 메인 루프로 넘긴다. 인터럽트가 길어지면 스텝 펄스 타이밍이 흔들린다.

## 7. 제어 경로에 두지 않는 것

| 항목 | 이유 |
| :--- | :--- |
| **WiFi · 네트워크** | 지터가 크고 상한이 보장되지 않는다. ESP32 WiFi는 ADC2와도 충돌한다 |
| **I2C 확장기 위의 안전 신호** | 버스가 지연·행업되면 안전 반응이 함께 늦어진다 [하드웨어 문서 4장과 동일 규칙] |
| **분석·설명 계층** | [RAG 설계 문서] 읽기 전용이며 제어 방향 연결이 존재하지 않는다 |
| **기준 영상 장치** | [PRD §3.1] 독립성이 성과 판정의 성립 조건이다 |

## 8. 통신 오류 처리

| 상황 | 반응 |
| :--- | :--- |
| CRC 불일치 | 프레임 폐기, 오류 카운터 증가. **동작하지 않는다** |
| SEQ 건너뜀 | 유실로 기록. 오래된 `PICK_PLAN`은 실행하지 않는다 |
| 알 수 없는 TYPE | 폐기 후 카운트. 상위 버전 프레임을 만나도 오동작하지 않는다 |
| 프레임 중간 타임아웃 | `SOF` 재동기 |
| `command_id` 불일치 ACK | [PRD §1.3] 해당 시도를 무효 처리 |
| 명령 송신 시 TX 큐 비어있지 않음 | `INVALID_TIMESTAMP` (3.4절) |
| 하트비트 300 ms 초과 | 5절의 상태별 반응 |
| 매핑 미수락 | `INVALID_CLOCK_MAPPING`, 새 픽 금지. 진행 중 동작의 안전성은 무관 (2절) |

**공통 원칙**: 통신 오류에서 **추정으로 메우지 않는다.** [PRD §1.3]이 "실패를 추정값으로 메우거나 마지막 지연값을 재사용해 픽하지 않는다"고 명시한 것과 같은 규칙을 프레임 층에도 적용한다.

---

## 9. 로그 전송

**[RAG 설계 문서 3장]** 은 수집기가 "제어 송신과 독립된 비동기 버퍼"여야 하며 "지연 또는 장애여도 제어를 막지 않는다"고 요구한다.

| 항목 | 방식 [제안] |
| :--- | :--- |
| 경로 | UART-B 또는 USB-CDC — **UART-A와 분리** (3.4절) |
| 버퍼 | ESP32 링 버퍼. 가득 차면 **가장 오래된 것부터 버리고 유실 개수를 기록**한다. 제어를 막지 않는다 |
| 형식 | append-only 레코드. 장치·펌웨어·스키마 버전 포함 |
| 시각 | ESP32 이벤트는 `C_ESP` 원시값으로 보낸다. **환산은 Pi에서, 수락된 매핑으로만** |
| 유실 | 조용히 넘어가지 않는다. 별도 오류로 남긴다 |
